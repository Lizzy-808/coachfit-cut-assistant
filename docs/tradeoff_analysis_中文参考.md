# CoachFit Cut Assistant —— 商业与技术权衡分析（中文参考版）

> 本文件是 `tradeoff_analysis.md` 的中文对照翻译，**仅供作者阅读理解，不用于提交**。以英文版为准。

LIU ZEYUAN · PE6201 B 组 · 期末项目

## 1. 核心决定

健身教练需要逐个客户判断：每天的热量摄入，对减脂来说是不是一个合理的缺口。在我的系统里，**由确定性的规则做出每一个判断，租用的语言模型只负责解释**：规则计算 BMR、TDEE、缺口标签和安全标记；`gpt-4o-mini` 为教练写一段简短的说明；然后由我写的两道检查来把关——只要说明里出现规则没有算出的数字，就退回固定模板；说明里漏掉的任何标记，由代码补上。范围之外：饮食记录、宏量营养素目标、蛋白质（原因见第 4 节）。

## 2. 方案对比

| 方案 | 判断正确率 | 每次成功检查的成本（美元） | 主要失败方式 |
|---|---|---|---|
| 教练手算 | — | 4.89 | 每个客户 5–10 分钟；不同教练取整方式不同 |
| LLM 直接分类（prompt 里给了公式） | 37–40% | 约 3.00† | 静默的算术错误 |
| 规则 + 固定模板 | 100%* | 1.08 | 措辞生硬 |
| **规则 + LLM 说明 + 检查（选中方案）** | 100%* | 1.08–1.77‡ | 说明写得流畅，但把关系说错 |

\*与在 Excel 中独立计算的标签对比，787 条有效 NHANES 记录。这检验的是我的算术，不是模型；模型的表现在第 4 节衡量。多数类基线 25%。†假设所有错误都能被发现；但这些错误是静默的，所以实际成本更高。‡分别对应实测的 20/20，以及它的 95% 置信下限 86%。

即使给了公式，LLM 在四轮测试中也只答对大约三分之一；在离分类边界 100 kcal 以内的案例上，只答对大约五分之一——而这恰恰是教练最需要帮助的地方。这是一个披着语言外衣的算术任务，所以模型应该放在决策之后，而不是之中。需要诚实面对的反面论点是第三行：模板本身就是正确的，而且免费，所以 LLM 能增加的只有可读性。第 3 节会算出它必须增加多少可读性才划算。

## 3. 值得做吗？（Class 5）

**每次成功检查的成本** = 变动成本 + (1 − 成功率) × 一次失败的成本。一次失败，就是教练必须手动重做的一条说明：7.5 分钟，按每小时 S$50（我所在健身房一节私教课的价格），以 9 月 28 日汇率 0.7823 美元/新币计算，等于 4.89 美元。每条说明的 token 成本只有 0.00014 美元——可以忽略不计。真正决定成本的是两项：规则主动转给教练的 22% 真实案例（主要是摄入低于安全下限），以及说明的出错率。在 v2 实测的 50% 成功率下，LLM 说明必须为教练每次节省 **225 秒**，才能胜过模板；在 v3 的 20/20 下，盈亏平衡点是零；在 86% 的置信下限下，需要节省 **63 秒**。这就是我的终止条件，在任何教练试用之前写下：如果说明读起来没有比模板快这么多，就去掉 LLM——所有的正确性都由规则保证。

**它买到了什么。** 只有规模：同样的检查，每个客户更便宜——这是一个效率项目，也按效率项目来论证。它没有通过免费标签测试：缺口估计是否正确，会体现在体重变化上，但体重是客户自己报的，也不会自动回流到系统里。范围（scope）也很弱：这套规则可以用来做营养师转介的初筛，但没有人提出过这个需求。

**数据就绪度。** NHANES 通过了"可获取"和"标准化"两项测试，但真实的健身房数据在"质量"和"一致性"上不合格：单日饮食回忆的少报非常普遍，以至于 18.5% 的 NHANES 成年人低于 1200/1500 kcal 的下限；客户的记录也因使用的 App 不同而各不一样。真正的瓶颈是运营模式——谁来记录摄入、每周记录、并在 PDPA 下取得同意——而不是模型。

## 4. 评估带来的改变

**主要指标（按老师的建议）：** 说明是否说到了规则标出的每一个标记，并且没有编造任何标记？由人工按 0/1 打分。

- **v2：10/20。** 没有一条说明编造标记；十个失败全部是遗漏。其中六个漏了"蛋白质未记录"——我的 NHANES 数据没有蛋白质这一列，是在 A1 整理数据时丢失的，因此蛋白质规则永远无法在真实数据上验证。我选择把蛋白质移出范围，而不是上线一条未经检验的规则。其余四个中，三个漏了记录误差提醒，一个漏了结论本身。
- **v3 只增加了一步：** 代码逐个检查标记，把说明漏掉的补上。在 **20 个之前从未使用过的新留出案例**上，我的评分是 **20/20**。按自动检查，模型自己只覆盖了 8/20，其余由检查补齐——和算术是同一个原则：必须正确的东西由代码强制保证，而不是要求模型做到。我的人工审查还发现了一个显示 bug（BMI 为 18.46 的客户被写成"BMI 18.5 低于 18.5"），已经修复。

**早期几轮塑造了设计。** 第 1 轮的检查以"编造数字"为由拒绝了 226 条说明中的 42 条——全部是误报：模型写的是"−90 kcal"，而我的正则表达式读成了 90。那一轮的评委也是 `gpt-4o-mini`，它同样把正确的建议判错了，所以我换成了 `deepseek-chat`，并用我的 20 个人工标签衡量它：一致率 75%，FAIL 精确率 60%，召回率 86%，而且在不同轮次之间不稳定。评委分数只是下限，不是指标。人工评分还显示，是规则本身让模型困惑：在 *appropriate*（合适）标签旁边标出"低于 BMR"，会让模型说"多吃点"；改写这个标记的措辞后，这类错误从 4/10 降到 0/10。v1 曾写出"150 g *高于* 128–176 g"，于是 prompt v2 预先写好了每一个比较结论；它提高了评委判定的正确率（87% → 97%），却降低了标记覆盖率（80% → 54%）——这个取舍被 v3 的检查消除了。

**"放弃判断"变成了"给出范围"。** 最初的做法是把离边界 50 kcal 以内的案例标记出来，但在 ±10% 的记录误差下会改变标签的案例中，它只抓到了 28%；真实案例中有 48% 对误差这么敏感，而要抓到 76%，就得把 38% 的客户都转去复核。现在工具会展示 ±10% 误差内所有可能的标签，只对安全案例强制复核——27 个安全案例全部正确转交。

## 5. 自建还是租用

自建：决策逻辑（24 个单元测试）、检查机制、评估集和评估工具。租用：模型（通过 OpenRouter 调用 `gpt-4o-mini`，改一行就能换）、评委、Streamlit。竞争对手下周二之前就能租到这些；他们无法很快复制的，是嵌入健身房每周工作流程中、取得了同意的客户数据——而这个项目目前还没有。没有尝试低代码：需要单元测试的算术不适合无代码工具。全部评估花费 0.30 美元。

## 6. 局限，以及什么情况下结论会改变

四个标签比数据本身更精细：10% 的记录误差和"合适"区间一样宽。我的人工评分覆盖 60 条说明，全部由我——系统的作者——评分；由教练评分的数据集是缺失的那一环。还没有真正的教练使用过这个工具，所以节省的时间——整个商业论证的核心——还没有被测量。负责任的使用：只面向健康成年人，拒绝 18 岁以下，不向模型发送任何身份信息，安全案例由人工复核（IMDA 框架），用检查机制防止错误信息（OWASP LLM09）。如果教练输入的是自由文本的饮食记录，模型就会进入决策路径，需要单独评估它的准确率。
